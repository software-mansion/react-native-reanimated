# Shared Element Transitions

:::caution

Shared Element Transitions is an experimental feature available [behind a feature flag](../guides/feature-flags.md#enable_shared_element_transitions), not recommended for production use yet. We are waiting for your feedback to improve the implementation.
:::

Shared Element Transitions allow you to smoothly transform a component from one screen into a component on another screen.

## Reference

```javascript
import Animated from 'react-native-reanimated';

const Stack = createNativeStackNavigator();

function One({ navigation }) {
  return (
    <>
      <Animated.View
        // highlight-start
        sharedTransitionTag="sharedTag"
        // highlight-end
      />
      <Button title="Two" onPress={() => navigation.navigate('Two')} />
    </>
  );
}

function Two({ navigation }) {
  return (
    <>
      <Animated.View
        // highlight-start
        sharedTransitionTag="sharedTag"
        // highlight-end
      />
      <Button title="One" onPress={() => navigation.navigate('One')} />
    </>
  );
}

export default function SharedElementExample() {
  return (
    <NavigationContainer>
      <Stack.Navigator>
        <Stack.Screen name="One" component={One} />
        <Stack.Screen name="Two" component={Two} />
      </Stack.Navigator>
    </NavigationContainer>
  );
}
```

## Overview

When Reanimated detects that the current top screen on the stack changes, it checks if there are components with the same `sharedTransitionTag` on the new and old top screen.

If it finds two matching components, it hides both of them by changing their opacity and creates a third view, that is displayed over the view hierarchy, that looks exactly like the source view, and is then animated to look like the target view. This implementation detail is subject to change as we might want to avoid creating a redundant instance of the same component.

After the animation is complete, the third view is removed, and the opacity of both original views is restored.

By default, every property that differs between the two views (for example `width`, `height`, `originX`, `originY`, `transform`, `backgroundColor`, `opacity` or the border radius) is animated with a duration of 500 ms using the [`withTiming`](../animations/withTiming.mdx) animation function.

## Usage

To create a shared transition animation between two components on different screens, simply assign the same `sharedTransitionTag` to both components. When you navigate between screens, the shared transition animation will automatically play.

If you want to use more than one shared view on the same screen, be sure to assign a **unique** shared tag to each component.

**Screen A**

```tsx {2}
<Animated.View
  sharedTransitionTag="sharedTag"
  style={{ width: 150, height: 150, backgroundColor: 'green' }}
/>
```

**Screen B**

```tsx {2}
<Animated.View
  sharedTransitionTag="sharedTag"
  style={{ width: 100, height: 100, backgroundColor: 'green' }}
/>
```

## Custom animation

You can customize the transition with the `SharedTransition` builder class. The available customization will be extended as the feature matures.

```tsx
import { SharedTransition } from 'react-native-reanimated';

const transition = SharedTransition.duration(550).springify();

function SharedView() {
  return (
    <Animated.View
      sharedTransitionTag="reanimatedTransition"
      // highlight-next-line
      sharedTransitionStyle={transition}
      style={{ backgroundColor: 'blue', width: 200, height: 100 }}
    />
  );
}
```

To define the animation yourself, use `SharedTransition.custom`. The worklet receives the values of the source view (`current*`), the values of the target view (`target*`) and the window size (`windowWidth`, `windowHeight`), and returns the animations for each property.

```tsx
const transition = SharedTransition.custom((values) => {
  'worklet';
  return {
    width: withSpring(values.targetWidth),
    height: withSpring(values.targetHeight),
    originX: withSpring(values.targetOriginX),
    originY: withSpring(values.targetOriginY),
  };
});
```

The values include `OriginX`, `OriginY`, `Width`, `Height`, `Opacity`, `BackgroundColor`, `Transform` (`{ matrix }`), `TransformOrigin`, `BorderRadius`, `BorderWidth`, `BorderColor` and the shadow properties, each with the `current` and the `target` prefix. Per-corner and per-side border values are included when one of the views sets them. `GlobalOriginX`, `GlobalOriginY` and `TransformMatrix` are kept for compatibility with Reanimated 3, and a returned `transformMatrix` is applied as the `transform`. Every animated property starts from its value in the source view, so animate the transform as a whole, with `transform: [{ matrix }]` or `transformMatrix`. The `custom` callback does not support individual transform operations such as `transform: [{ scale: withTiming(2) }]`.

### Progress-based animation

On iOS, back navigation (a swipe gesture or the back button) runs a progress-based transition: the shared view follows the progress of the screen transition, and a cancelled swipe returns it to its place. By default every property is interpolated linearly. Use `progressAnimation` to compute the style for a given progress (0-1) yourself:

```tsx
const transition = SharedTransition.custom((values) => {
  'worklet';
  return { width: withSpring(values.targetWidth) };
}).progressAnimation((values, progress) => {
  'worklet';
  return {
    width: values.currentWidth + progress * (values.targetWidth - values.currentWidth),
  };
});
```

Call `.defaultTransitionType(SharedTransitionType.PROGRESS_ANIMATION)` to use the progress-based animation for every transition. During iOS back navigation, the screen transition controls progress. Otherwise, the builder settings control progress: for example, `.duration(800)` animates progress from 0 to 1 over 800 ms, while `.springify()` uses a spring animation.

### Typing separate callbacks

When defining callbacks separately from the builder, use the exported `CustomSharedTransitionAnimation` and `ProgressSharedTransitionAnimation` types:

```tsx
import {
  SharedTransition,
  withSpring,
  type CustomSharedTransitionAnimation,
  type ProgressSharedTransitionAnimation,
} from 'react-native-reanimated';

const customAnimation: CustomSharedTransitionAnimation = (values) => {
  'worklet';
  return { width: withSpring(values.targetWidth) };
};

const progressAnimation: ProgressSharedTransitionAnimation = (values, progress) => {
  'worklet';
  return {
    width: values.currentWidth + progress * (values.targetWidth - values.currentWidth),
  };
};

const transition = SharedTransition.custom(customAnimation).progressAnimation(progressAnimation);
```

### Remarks

Callbacks passed to `custom` and `progressAnimation` must include the `'worklet'` directive. These callbacks are not automatically workletized, whether defined inline or separately.

## Current limitations

- Only the [native stack](https://reactnavigation.org/docs/native-stack-navigator/) is supported.
- The [Tab navigator](https://reactnavigation.org/docs/bottom-tab-navigator/) is not supported yet, using it in on path that uses shared transitions may result in no animation being ran.
- Transitions with native modals (using `transparentModal`) don't work properly on iOS (the modal is obstructing the Shared Element).
- On iOS you can encounter some issues with the vertical positioning of transitioning views. This is due to issues with header height information propagation.
- There are some performance bottlenecks, that stem from transforms being recalculated too eagerly.
- We have to use a workaround for react-native-screens to not keep a snapshot of the transitioning view on the popped screen. Currently the fix is available in 3.19+ versions.
- Enabling the feature flag causes the `zIndex` of views with exiting animations to change (they are brought to the front). This differs from the current behavior in Reanimated 4.
- Sometimes on a fast refresh, the transition will run for elements that are on the same screen. It can happen when the navigator is wrapped with a context provider, and the native view that represents the screen changed, so the SET logic was triggered.
