  # Limitations and troubleshooting
</Badges>

## The view does not move

Check these points:

- Both views have the same [`sharedTransitionTag`](./shared-transition-props.mdx#sharedtransitiontag), and each tag shows only once on a screen.
- Both views are animated components of the same native type, for example `Animated.View` and `Animated.View`. With different types, a debug build stops on an assertion. A release build moves the view, but the view takes only the position, the size and the transform of the other view.
- The tag is on a component with its own native view. A `Text` inside another `Text` has no native view, so it cannot be a shared view.
- On Android, a view with its own `nativeID` gets its transition only after it mounts. If it mounts in the same update that changes `isActive`, it can miss that transition. Remove the `nativeID`, or mount the view before that update.
- Each screen is in a [`SharedTransitionBoundary`](./screens-and-boundaries.mdx#sharedtransitionboundary), and `isActive` changes from the old screen to the new screen when you navigate.
- No boundary that is always active is around the boundaries of your screens.
- The view is not in a native header. React Navigation renders `headerTitle`, `headerLeft` and `headerRight` outside of the screen, so they are outside of the boundary of the screen. A boundary in the header becomes the active boundary instead of the boundary of the screen. Put the view in the content of the screen, or hide the native header and render your own header in the screen.
- On iOS, both boundaries must use the `UIWindow` of the React Native root view or a modal presented over it. The view does not move to or from a boundary in another window.
- On iOS, the view lands only when the screen of the target is in the window. A transition with a built-in animation starts at once and moves to the place that React Native gives the target until the screen is in the window. If the screen is not in the window when the animation ends and 500 ms have passed since the boundary became active, the view does not land, the two views show in their own places, and the callback gets `false`. A transition with a custom animation or a timed progress animation starts when the screen is in the window. If the screen is not in the window after 500 ms, the transition does not start, and its callback gets `false`. The two views show in their own places.
- The [`USE_LEGACY_LAYOUT_ANIMATIONS_PROXY`](../guides/feature-flags.md#use_legacy_layout_animations_proxy) feature flag is off. The legacy layout animations proxy does not support Shared Element Transitions.

## Modals and sheets on Android

On Android, a shared view can move between two views in the same React Native `Modal`. The moving view stays in the window of the `Modal`. If the `Modal` closes during the transition, the transition stops, and its callback gets `false`.

A shared view does not move between the screen and a `Modal`, between two different `Modal`s, or to or from a native-overlay sheet. The two views stay visible in their own places. A `Modal` inside another `Modal` counts as a different `Modal`. This limit does not apply to iOS.

## Updates during the transition

- Changes that React makes to the props or the layout of the moving view itself wait until the transition ends. Then they show at once, which can look like a jump. This includes changes from React state and from `useAnimatedStyle` updates that go through React. The children of the moving view can update during the move.
- If the target view changes only its style during the transition, the moving view does not animate to the new style. The new style shows when the transition ends. A shared view that waits for its parent (see below) animates to a new style of its target.
- Built-in timed transitions follow the current transforms of the target's parents. These changes do not restart the transition. A layout change of a parent that moves the target is a layout change of the target (see below). Timed custom animations and timed progress animations keep their target snapshot.
- If you use `IOS_SYNCHRONOUSLY_UPDATE_UI_PROPS` or `ANDROID_SYNCHRONOUSLY_UPDATE_UI_PROPS`, enable [`TRACK_SYNCHRONOUS_PROPS_IN_LAYOUT_ANIMATIONS`](../guides/feature-flags.md#track_synchronous_props_in_layout_animations) while the target's parents move. This lets Shared Element Transitions read their current transforms.
- With [`USE_ANIMATION_BACKEND`](../guides/feature-flags.md#use_animation_backend), Shared Element Transitions do not read the transforms that the animation backend applies to the target's parents. The moving view follows the last committed transforms. Disable the backend if the target's parents move during a transition.
- If the layout of the target changes during a timed transition, the view starts a new move from its current frame. This new move can use the full duration again. A spring starts a new geometry animation from rest.
- If React removes the target view during the transition and the source view stays, the view moves to the last place of the target. Then the source view shows in its own place at once, and the callback gets `true`. On iOS, a transition that still waits for the screen of its target to join the window ends at once, and its callback gets `false`. If the same update makes the source screen active again, for example `navigation.goBack()`, the view moves back to the source.
- A shared view inside another shared view moves inside the moving parent when its target is inside the target of the parent. It follows the path of the parent. When the two use different timing, it moves relative to the parent, not along its own path on screen. If its own transition ends first, it waits inside the parent until the transition of the parent ends. A built-in transition keeps the completed view at its current target while it waits.
- A nested shared view moves on its own, above other views, when it is nested on only one of the screens, when its new target after a retarget is outside the target of the parent, or when React moves it out of the parent or removes a view between it and the parent. It keeps its frame on screen when it starts to move on its own. A running built-in transition then starts a new move from this frame.
- A text input that the target screen focuses when it opens shows the keyboard during the transition. If the keyboard moves the target view, for example in a `KeyboardAvoidingView`, the moving view changes its course. Focus the input after the shared transition ends, for example in a callback set with `.withCallback()` on the `SharedTransition` of the outermost shared view, when `finished` is `true`. A shared view that moves inside its parent lands with the parent, and its callback runs then. The `transitionEnd` event of the screen can come while the shared view is still moving.
- Avoid replacing an endpoint with a new native view during a native back gesture. SET does not retarget that replacement.

## Known issues

- On iOS, a screen that a native stack shows for the first time gets its header size a moment later. A view that flies to such a screen, for example to the first screen of a nested stack, can first move too high and then move down.
- The first time that the user opens a tab, a view that flies to the new tab screen can stay at its old place for a moment and then jump to its target. On iOS this happens with the default `detachInactiveScreens` of bottom tabs, and `detachInactiveScreens={false}` avoids it. On Android it happens with `freezeOnBlur`. Later visits of the tab run the transition.
- On iOS, if the header of a covered screen changes, for example after a theme change, a view that goes back to this screen can stop at the old place and then jump.
- Reanimated does not see screen animations that run with the native driver of React Native `Animated`, for example the screen animations of `@react-navigation/stack` or the `fade` animation of bottom tabs. A view that flies to such a screen goes to the place and the opacity where the screen starts its animation, for example off the screen or fully transparent, and then jumps when the animation ends. Use `@react-navigation/native-stack`, or bottom tabs without an animation.
- A nested shared view does not follow a scroll or a layout animation of a view between it and its moving parent. A view between them keeps its source size and place during the move: its `overflow: hidden` clips the nested view to the source bounds, and its background shows at the source size. When the parent shrinks, the larger view can show outside of the parent. Give such a view its own `sharedTransitionTag`, so that it moves to its own match, or put the clipping and the background on the shared parent.
- During development, a Fast Refresh can start a transition between the old and the new version of a view on the same screen. This does not happen in release builds.

## Videos and media

The moving view keeps its own content, for example an image or a video player. For images:

- The image of the moving view keeps its `resizeMode`. The `resizeMode` of the target, for example `contain` after `cover`, shows when the transition ends.
- The target image shows when the transition ends, also when it is still loading. Then the user sees its placeholder, and if the user goes back before it loads, the empty image moves back. To avoid this, use the same image source on both screens. For example, use the thumbnail as the shared image on both screens, and show the full image above it on the details screen as a separate image that fades in when it loads.

To reduce video glitches:

- On iOS, give the same video player to the video views on both screens. Then the playback continues from the same position.
- On Android, expo-video cannot show one player in two mounted views. Use a separate player on each screen. The two players can be at different positions, so the video can jump when the target shows. See the [expo-video guide](https://docs.expo.dev/versions/latest/sdk/video/#using-the-videoplayer-directly).
- On Android, use a `TextureView` for a video that moves over other content, for example `surfaceType="textureView"` on the expo-video `VideoView`. A `TextureView` draws as a part of the view hierarchy, so it moves and overlaps like other views. It can cost more to draw and cannot show DRM content. Set the surface type when you create the video view, and do not change it at runtime. See the [Android `TextureView` reference](https://developer.android.com/reference/android/view/TextureView).

Reanimated keeps the native view on screen during the transition, but not the React component that owns it. `useVideoPlayer` releases its player when the component that created it unmounts, also when the view still shows. For example, `navigation.goBack()` or the Android back button can unmount the screen while its shared view still moves. To keep the player alive:

- Create the player in a component that stays mounted, for example above the navigator.
- Or create it with `createVideoPlayer` and call `release()` when no view needs it any more.
