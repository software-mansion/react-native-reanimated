# Debugging Worklet Runtimes

Every [Worklet Runtime](/docs/fundamentals/runtimeKinds) is registered as a separate debug target in [React Native DevTools](https://reactnative.dev/docs/react-native-devtools).
This lets you use the Console, Sources and Performance panels on the [UI Runtime](/docs/fundamentals/runtimeKinds#ui-runtime) and on every [Worker Runtime](/docs/fundamentals/runtimeKinds#worker-runtime) created with [`createWorkletRuntime`](/docs/threading/createWorkletRuntime), the same way you use them on the [RN Runtime](/docs/fundamentals/runtimeKinds#rn-runtime).

## Opening a Worklet Runtime in DevTools

Press <kbd>j</kbd> in the Metro terminal. With more than one target connected, Metro lists them and asks you to pick one by number.
The RN Runtime is listed as `React Native Bridgeless` and all Worklet Runtimes together as `Worklet Runtimes`.

In the `Worklet Runtimes` window, the UI Runtime is the main thread and every Worker Runtime created with `createWorkletRuntime` is a separate thread named `Worklet Runtime (<name>)`.
Switch between them in the _Threads_ pane of the Sources panel, or with the context selector of the Console panel. Worker Runtimes created later show up as soon as they exist.

You can also list the targets with `http://localhost:8081/json` and open the `devtoolsFrontendUrl` of the `Worklet Runtimes` page, or add `localhost:8081` under _Discover network targets_ in `chrome://inspect`.

## What works

- `console` calls made on the runtime are shown in the DevTools Console and are still forwarded to the RN Runtime console.
- Breakpoints and `debugger` statements pause the runtime.
- The Performance panel records a CPU profile of the runtime.

## Limitations

- Only runtimes with locking enabled and an async queue are attached. Runtimes created with `enableLocking: false` or `useDefaultQueue: false` without a custom queue are not debuggable.
- Pausing the UI Runtime pauses the main thread of the app, so the UI stops responding until you resume. On Android, touching the app while it is paused can trigger the "App isn't responding" dialog; choose _Wait_.
- A Worklet Runtime cannot be reloaded on its own. Reloading from a Worklet Runtime target reloads the whole app.

## How it works

Worklets opens its own connection to the Metro inspector proxy, separate from the one React Native uses. React Native dispatches inspector messages on the main thread, which is also where the UI Runtime runs, so a paused UI Runtime could never receive the resume command through it. The Worklets connection dispatches messages on a dedicated thread instead. It is listed by Metro as a second device with the same name and app id, with a single `Worklet Runtimes` page.

Inside a DevTools session of that page, Worker Runtimes are exposed through the CDP `Target` domain as `worker` targets, the same mechanism browsers use to show Web Workers next to the page. DevTools attaches to them automatically and addresses each one with its own session id.
