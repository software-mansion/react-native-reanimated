# Your first worklet

It's time to try ou the multithreading model we outlined in the [previous chapter](link).

Let's start small - dispatching functions that perform only a `console.log` on different runtimes. We'll print the TID of the executing thread too, to show that they indeed are dispatched to different thread, with `getCurrentThreadId()` function. This function prints the [`std::get_thread_id`](link) result.

```js
const worker = createWorkletRuntime();

function logTid() {
    'worklet'; // TODO: explain why its useful
    console.log(getCurrentThreadId());
}

scheduleOnUI(logTid);
scheduleOnRuntime(worker, logTid);
```

All of the log invocations returned different TID, because we used `schedule` methods, which dispatch the worklet to threads dedicated to a given runtime.

Note: you can drop the worklet directive. React Native Worklets Babel plugin [automatically detects](link) which functions should be marked as worklets *within the same file* and attaches the directive for you. Future examples will omit the directive whenever applicable.

However, Worklets expose a handful of imperative APIs and we can obtain the runtimes exclusively and invoke our worklet on them synchronously, from the same thread.

```js
const worker = createWorkletRuntime();

function logTid() {
    'worklet';
    console.log(getCurrentThreadId());
}

logTid();
runOnUISync(logTid);
runOnRuntimeSync(worker, logTid);
```

Note that all 3 logs gave us the same result, there was no thread hopping involved. Knowing when to delegate something asynchronously and when to do it synchronously is the difference between smooth user experience and a bad one. Rule of thumb says that if the operation is not UI critical, it should be dispatched asynchronously.

## Returning results

Logging might not seem particularly useful and often times you want to return a result of worklet calculation to the scheduling runtime.

### Synchronously

Note that `schedule` functions do not return a value - but `runOnRuntimeSync` does.

```js
const worker = createWorkletRuntime();

function foo() {
    return 42;
}

const scheduleResult = scheduleOnRuntime(worker, foo); // TS error - no return value.
const syncResult = runOnRuntimeSync(worker, foo); // 42
```

However, it's not particularly useful to dispatch `foo` synchronously, as we could've just run on the same runtime, by invoking foo:

```js
const syncResult = foo(); // 42
```

Therefore, we have to return it asynchronously. We'll explore when it's useful to actually return a value synchronously in future sections.

### Asynchronously

For asynchronous returns, i.e. results of complex calculations, you can use `runOnUIAsync` or `runOnRuntimeAsync` family of functions. They return an awaitable promise.

```js
const worker = createWorkletRuntime();

function complexTask() {
    return 42;
}

const result = await runOnRuntimeAsync(worker, complexTask); 
```

The scheduling runtime is free to keep executing JavaScript code unless you await the returned promise.

### With callbacks

Often times, you'll want to update your app's React state based on a result of a worklet executed on another thread. You might be tempted to write something like this:

```js
const worker = createWorkletRuntime();

function Component() {
    const [state, setState] = useState();
    // code ...
    scheduleOnRuntime(worker, () => {
        const result = doImportantStuff();
        setState(result); // crash!
    });
    // code ...
}
```

This is a common pitfall, and to understand why it crashes, we have to look how it looks in the memory of our app.

Because `setState` is passed to the Worklet Runtime as a pointer, you can't just invoke it, but instead you have to explicitly invoke it back on the RN Runtime with `scheduleOnRN`.

```js
const worker = createWorkletRuntime();

function Component() {
    const [state, setState] = useState();
    // code ...
    scheduleOnRuntime(worker, () => {
        const result = doImportantStuff();
        scheduleOnRN(setState, result); // crash!
    });
    // code ...
}
```

Alternatively, you can solve this issue with a promise and `runOnRuntimeAsync` function:

```js
const worker = createWorkletRuntime();

function Component() {
    const [state, setState] = useState();
    // code ...
    runOnRuntimeAsync(worker, () => {
        const result = doImportantStuff();
        return result;
    }).then(result => setState(result));
    // code ...
}
```

## Synchronizing with data

Previous examples showed us how to return the result of a singular worklet at the point of its invocation. What if we had a long-running task, perhaps several of them, yielding results continuously, but we wanted to poll the data only occasionally?

```js
const worker = createWorkletRuntime();

function taskWrapper() {
    let result = -1;

    function task() {
        result++;
    }

    setInterval(task, 10);
};

scheduleOnRuntime(worker, taskWrapper);
```

There's no easy way to access locally declared `result` variable.

### Using the global object

Simplest solution here would be to store the result in the global object:

```js
const worker = createWorkletRuntime();

function taskWrapper() {
    globalThis.result = -1;

    function task() {
        globalThis.result++;
    }

    setInterval(task, 10);
};

scheduleOnRuntime(worker, taskWrapper);
```

And then poll it with another function call, either synchronously or asynchronously:

```js
function poll() {
    return globalThis.result;
}

const asyncResult = runOnRuntimeAsync(worker, poll); // remember to await it later
const syncResult = runOnRuntimeSync(worker, poll);
```

However, this code doesn't scale well and it's generally a bad practice to use the global object like this, it should be a last resort escape hatch.
